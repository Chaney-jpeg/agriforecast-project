# Guided database learning path

We will build the AgriForecast database together in small steps. You will run and explain the SQL yourself; I will help design each part, review errors, and guide the next step. We will use PostgreSQL directly so the exercises teach transferable SQL and database fundamentals. Supabase can be considered later as a managed PostgreSQL host. The running prototype is a Next.js app; the database will be connected to its existing server-side API routes when we reach that milestone. Keep the current dev server running and use a separate VS Code terminal for database commands.

## Milestones

1. Install/check PostgreSQL and connect locally.
2. Create a project database and practice basic SQL.
3. Draw the entity relationships from the prototype and choose primary keys.
4. Create core tables with appropriate types, keys, checks, and foreign keys.
5. Insert a small, clearly labeled demo dataset.
6. Query the data with joins and aggregations.
7. Add versioned rules and advisory history with enough provenance to reproduce decisions.
8. Review backups, permissions, migrations, and how the Next.js server-side code connects securely.

We will pause at each milestone for you to run the commands and bring back the output. I will not skip ahead and build the whole schema for you.

## Step 5 — Create the `farms` table (complete)

A farm is a location and context record. Keep it separate from a planting/crop cycle: one farm can have many crop cycles, and each cycle will refer to a row in `crops`.

```sql
CREATE TABLE public.farms (
    farm_id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    farm_name text NOT NULL,
    county text NOT NULL,
    ward text,
    latitude numeric(8,5) NOT NULL CHECK (latitude BETWEEN -90 AND 90),
    longitude numeric(8,5) NOT NULL CHECK (longitude BETWEEN -180 AND 180),
    soil_type text CHECK (soil_type IN ('sandy', 'loam', 'clay'))
);
```

Latitude and longitude checks prevent impossible coordinate values. Soil is optional because the prototype supports unknown soil; when entered, it must be one of the current categories. County is required for location context. The user confirmed the table was created successfully. The target pilot county remains undecided, so use clearly labeled practice data only.

## Step 7 — Create `crop_cycles` with foreign keys (complete)

A crop cycle represents a planting on a specific farm. It references both `farms` and `crops`, so PostgreSQL can prevent a planting from pointing to a farm or crop that does not exist.

```sql
CREATE TABLE public.crop_cycles (
    crop_cycle_id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    farm_id integer NOT NULL REFERENCES public.farms(farm_id) ON DELETE CASCADE,
    crop_id integer NOT NULL REFERENCES public.crops(crop_id),
    planting_date date,
    maturity_class text CHECK (maturity_class IN ('early', 'medium', 'late')),
    area_hectares numeric(8,2) CHECK (area_hectares > 0)
);
```

`farm_id` and `crop_id` are foreign keys. Deleting a farm removes its crop-cycle records; deleting a crop referenced by a cycle is blocked unless cycles are handled first. Planting date and maturity class can be unknown. The user confirmed that the table was created.

## Step 10 — Join the three tables (complete)

Retrieve a readable crop-cycle view by joining the child record to its farm and crop catalogue rows:

```sql
SELECT
    cc.crop_cycle_id,
    f.farm_name,
    c.name_en AS crop,
    cc.planting_date,
    cc.maturity_class,
    cc.area_hectares
FROM public.crop_cycles AS cc
JOIN public.farms AS f ON f.farm_id = cc.farm_id
JOIN public.crops AS c ON c.crop_id = cc.crop_id;
```

Each `JOIN` matches foreign-key values to the parent table's primary key. `AS` gives short aliases for readability. Optional fields should appear as `NULL`, meaning unknown/not entered; that is different from a real zero value. The user confirmed the query worked.

## Step 15 — Create daily weather records (complete)

The prototype's bundle contains daily weather values. Keep observations and short-range forecasts distinct, and retain the issue time for forecast records. `NULL` means a measurement was unavailable; it does not mean zero.

```sql
CREATE TABLE public.weather_records (
    weather_record_id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    location_id integer NOT NULL REFERENCES public.weather_locations(location_id),
    source_id integer NOT NULL REFERENCES public.weather_sources(source_id),
    data_type text NOT NULL CHECK (data_type IN ('observation', 'forecast')),
    issued_at timestamptz,
    valid_date date NOT NULL,
    rainfall_mm numeric(7,2) CHECK (rainfall_mm >= 0),
    min_temp_c numeric(5,2),
    max_temp_c numeric(5,2),
    hours_rh90 numeric(4,1) CHECK (hours_rh90 BETWEEN 0 AND 24),
    max_thi numeric(5,2),
    fetched_at timestamptz NOT NULL DEFAULT now(),
    CHECK (min_temp_c IS NULL OR max_temp_c IS NULL OR min_temp_c <= max_temp_c),
    CHECK (data_type = 'observation' OR issued_at IS NOT NULL)
);
```

The final two checks require minimum temperature not to exceed maximum temperature (when both exist) and require issue time for forecasts. Seasonal outlooks need a different shape and will be designed separately instead of forcing them into daily rows. The user confirmed the table was created.

## Step 19 — Create livestock groups (complete)

The prototype's livestock context is farm-specific. Store each animal group separately, allowing a farm to have more than one group.

```sql
CREATE TABLE public.livestock_groups (
    livestock_group_id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    farm_id integer NOT NULL REFERENCES public.farms(farm_id) ON DELETE CASCADE,
    species text NOT NULL CHECK (species IN ('cattle', 'goat', 'sheep', 'poultry')),
    animal_count integer CHECK (animal_count > 0),
    shade_available boolean,
    water_source text CHECK (water_source IN ('reliable', 'unreliable', 'far')),
    pasture_condition text CHECK (pasture_condition IN ('good', 'fair', 'poor'))
);
```

The category checks constrain spelling to values the prototype understands. `NULL` means the farmer has not provided that information; it is not the same as `false` or a known poor condition. The user confirmed the table was created.

## Step 23 — Create the advisory parent table (complete)

Store each assessment's headline and status in one row. The supporting reasons, actions, missing inputs, and assumptions will be child rows in the next step because an advisory can have several of each.

```sql
CREATE TABLE public.advisories (
    advisory_id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    farm_id integer NOT NULL REFERENCES public.farms(farm_id) ON DELETE CASCADE,
    crop_cycle_id integer REFERENCES public.crop_cycles(crop_cycle_id),
    livestock_group_id integer REFERENCES public.livestock_groups(livestock_group_id),
    rule_version_id integer NOT NULL REFERENCES public.rule_versions(rule_version_id),
    topic text NOT NULL CHECK (topic IN ('planting', 'disease', 'livestock')),
    level text NOT NULL CHECK (level IN ('go', 'prepare', 'wait', 'caution', 'info', 'low', 'moderate', 'high', 'severe')),
    confidence text NOT NULL CHECK (confidence IN ('low', 'medium', 'high')),
    evidence_type text NOT NULL CHECK (evidence_type IN ('forecast_based_estimate', 'backtested_model', 'locally_validated')),
    headline_en text NOT NULL,
    headline_sw text NOT NULL,
    confidence_note_en text,
    confidence_note_sw text,
    generated_at timestamptz NOT NULL DEFAULT now(),
    valid_until timestamptz
);
```

This table links an assessment to its farm and rule version. Crop-cycle and livestock-group links are optional because some assessments may happen before a specific cycle/group is registered. The current prototype should use `forecast_based_estimate` and its placeholder rule version. The user confirmed the table was created.

## Step 24 — Create advisory detail items

Represent each reason/action/assumption/missing-input/would-change item as an ordered child row, with the English and Swahili text kept together.

```sql
CREATE TABLE public.advisory_items (
    advisory_item_id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    advisory_id integer NOT NULL REFERENCES public.advisories(advisory_id) ON DELETE CASCADE,
    item_type text NOT NULL CHECK (item_type IN ('reason', 'action', 'assumption', 'missing', 'would_change')),
    display_order integer NOT NULL CHECK (display_order > 0),
    field_key text CHECK (field_key IN ('crop', 'planting_date', 'soil', 'variety', 'species', 'shade', 'water_source', 'pasture')),
    text_en text NOT NULL,
    text_sw text NOT NULL,
    UNIQUE (advisory_id, item_type, display_order),
    CHECK ((item_type = 'missing' AND field_key IS NOT NULL) OR (item_type <> 'missing' AND field_key IS NULL))
);
```

For `missing`, `field_key` identifies which input is missing. `display_order` preserves the order of each list in the prototype. Deleting an advisory also removes its detail rows.

## Design guardrails

- A farm belongs to a user once authentication is introduced; farm queries must enforce ownership.
- A crop cycle is separate from a crop catalogue row: the catalogue describes the crop, while a cycle records what/when a farm planted.
- Weather values need units, data type, source, issue time, and valid time. Missing rainfall is different from 0 mm.
- Seasonal outlooks, short-range forecasts, observations, and demo scenarios must not be conflated.
- Rules should carry a version and citations; placeholder rules must be visibly marked as unvalidated.
- A saved advisory should retain enough input/provenance detail to explain why it was produced.
